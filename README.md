## 1. 목표·이유

머신비전 검사 회사 공고는 대부분 C++를 요구한다. 파이썬으로 만든 검사 모델은 있었지만
"C++로 검사 코드를 짜 봤다"고 말할 근거가 없었다. 말로 때우는 대신 실제로 짜고,
**같은 입력에서 파이썬 기준 구현과 결과가 일치하는지**로 정확성을 증명하기로 했다.

2차에서는 목표를 하나 더 얹었다. 1차의 결론은 "두 구현이 일치한다"까지였고
**검출이 잘 되는지는 재지 않은 상태**였다. 결함 14개를 심었는데 후보가 235개 나온 것을
"많다"고 눈으로 판단했을 뿐이라, 심은 결함의 위치를 정답으로 남기고 정밀도·재현율로 바꿨다.

## 2. 무엇을 만들었나

의존성 없는 C++17 단일 파일(`src/inspect_core.cpp`). 외부 라이브러리를 쓰지 않은 이유는
OpenCV를 부르면 "OpenCV를 썼다"가 되고 알고리즘을 짰다는 증거는 남지 않기 때문이다.

파이프라인:

1. PGM(P5) 읽기 — 주석 줄 처리 포함
2. 노이즈 제거 — 3x3 median(테두리 clamp 확장) 또는 끄기. **선택 가능**
3. 이진화 — **Otsu 전역** 또는 **Sauvola 국소 적응**. 선택 가능
   - Otsu: 클래스 간 분산 최대화, 동점이면 작은 t
   - Sauvola: `T(x,y) = m(x,y) · (1 + k·(s(x,y)/R − 1))`, R=128. 창 안의 평균·표준편차를
     **적분영상으로 O(1)** 에 구한다. 창은 경계에서 잘라 쓰고 잘린 만큼 픽셀 수를 다시 센다
4. 8-연결 연결요소 라벨링 — 2-pass union-find, 라벨을 좌상단 우선으로 재부여
5. blob 통계 — 면적, bbox, 무게중심
6. 면적 하한으로 결함 후보 선별 후 CSV 출력

```
./inspect_core <input.pgm> <min_area> <out.csv> [otsu|sauvola] [window] [k] [median3|none]
```

측정 도구 두 개를 같이 뒀다.

- `tools/eval_binarize.py` — 정답 대비 정밀도·재현율·F1. `--sweep` 으로 격자 탐색
- `tools/sweep_noise.py` — 노이즈 세기를 바꿔 가며 median 유/무를 비교

## 3. 검증 방법

`ref/reference.py`가 같은 파이프라인을 numpy로 구현한다. 단 **라벨링만은 `scipy.ndimage.label`**을
쓴다 — 같은 알고리즘을 두 언어로 옮겨 적으면 같은 실수를 두 번 하게 되므로,
그 부분은 독립 구현을 기준으로 삼아야 대조가 의미 있다.

Sauvola를 추가할 때도 같은 규칙을 지켰다. 적분영상은 양쪽 다 int64로 누적하고 분산은
`E[x²] − E[x]²` 로 구한 뒤 음수를 0으로 자르는 것까지 **연산 순서를 맞췄다**. 부동소수 결과가
한 비트라도 갈리면 임계 근처 픽셀의 전경/배경이 뒤집혀 대조가 깨지기 때문이다.

`ref/make_data.py`는 이제 심은 결함의 위치를 `*_truth.csv` 로 같이 남긴다. RNG 호출 순서를
바꾸지 않아 **같은 seed에서 영상 바이트는 1차 때와 동일하다**(`cmp` 로 확인).

```bash
export PATH="/c/Users/apple/AppData/Local/Microsoft/WinGet/Packages/BrechtSanders.WinLibs.POSIX.UCRT_Microsoft.Winget.Source_8wekyb3d8bbwe/mingw64/bin:$PATH"
g++ -std=c++17 -O2 -Wall -Wextra -static -o inspect_core.exe src/inspect_core.cpp
python ref/make_data.py data/frame_512.pgm 512 512 14 42

# 두 구현 대조 (전역 / 국소 각각)
./inspect_core.exe data/frame_512.pgm 6 out/cpp.csv
python ref/reference.py data/frame_512.pgm 6 out/ref.csv
diff out/cpp.csv out/ref.csv

./inspect_core.exe data/frame_512.pgm 6 out/cpp_sauvola.csv sauvola 31 0.20 none
python ref/reference.py data/frame_512.pgm 6 out/ref_sauvola.csv sauvola 31 0.20 none
diff out/cpp_sauvola.csv out/ref_sauvola.csv

# 검출 성능 측정
python tools/eval_binarize.py --sweep data/frame_512.pgm
python tools/sweep_noise.py
```

## 4. 측정 결과 (512x512, 결함 14개, seed 42)

### 4.1 두 구현의 일치

세 설정 모두 **출력 CSV가 바이트 단위로 동일**했다(`diff` 무출력). 면적·bbox·무게중심 전부 일치.

| 설정 | C++17 (`-O2`) | Python (numpy+scipy) | 비 |
|---|---:|---:|---:|
| Otsu + median3 | 19.2 ms | 381.9 ms | 19.9배 |
| Sauvola + median3 | 19.1 ms | 53.5 ms | 2.8배 |
| **Sauvola + median 없음** | **2.58 ms** | 36.0 ms | 13.9배 |

(각 5회·3회 실행의 중앙값. 같은 알고리즘이므로 순수 언어·구현 차이다.)

> Python 쪽 배수가 설정마다 크게 다른 이유는 numpy가 벡터화로 이기는 연산과 아닌 연산이
> 갈리기 때문이다. median3는 9장을 쌓아 `np.median`을 부르는 구조라 파이썬이 특히 느리고,
> Sauvola는 누적합이라 numpy가 잘한다. **"파이썬 대비 몇 배"는 알고리즘마다 다르므로
> 하나의 배수로 말하면 안 된다.**

### 4.2 검출 성능 — 전역 임계 vs 국소 적응

심은 결함 14개를 정답으로 두고 후보 bbox와의 겹침으로 채점했다(`tools/eval_binarize.py`).

| 이진화 | 노이즈 제거 | 후보 | 검출 | 오검출 | 정밀도 | 재현율 | **F1** |
|---|---|---:|---:|---:|---:|---:|---:|
| Otsu (전역) | median3 | 235 | 14/14 | 228 | 0.030 | 1.000 | **0.058** |
| Sauvola (국소) | median3 | 12 | 12/14 | 0 | 1.000 | 0.857 | **0.923** |
| **Sauvola (국소)** | **없음** | **14** | **14/14** | **0** | **1.000** | **1.000** | **1.000** |

Otsu의 재현율이 1.000인 것은 성능이 아니라 **화면의 상당 부분을 전경으로 잡아서** 생긴 값이다.
정밀도 0.030이 실제 상태다. 재현율만 보면 정반대의 결론이 나오므로 둘을 같이 본다.

`--sweep` 으로 면적 하한(4·6·10·20), Sauvola 계수 k(0.10~0.40), 창 크기(15~101)를 격자로 돌렸다.
**창 크기는 15에서 101까지 결과가 동일**했고, k는 0.40부터 재현율이 깎였다.
파라미터를 눈대중으로 고르지 않기 위한 확인이다.

## 5. 1차에 남긴 문제를 닫은 과정

### 5.1 전역 임계의 한계 — 조명 기울기가 배경째 전경이 된다

1차에서 "결함 14개를 심었는데 후보 235개"의 원인을 조명 불균일로 특정해 뒀다.
Sauvola는 창 안의 평균을 기준선으로 삼으므로 완만한 조명 기울기를 배경으로 흡수한다.
바꾸자 후보가 **235개에서 12개로, 오검출이 228개에서 0개로** 떨어졌다(F1 0.058 → 0.923).

### 5.2 그런데 재현율이 0.857 — 놓친 2개가 둘 다 스크래치였다

정답과 하나씩 맞춰 보니 놓친 것은 bbox 폭이 4px·2px인 **가늘고 세로로 긴 스크래치 2개**였다.
원인을 이진화로 의심했는데, 원본과 median 통과 후의 국소 대비를 재 보니 아니었다.

| 결함 | 배경 | 원본 최소값(대비) | median3 후 최소값(대비) |
|---|---:|---:|---:|
| 놓친 스크래치 A (폭 4px) | 179 | 83 (**96**) | 173 (**6**) |
| 놓친 스크래치 B (폭 2px) | 177 | 79 (**98**) | 171 (**6**) |
| 검출된 스크래치 (폭 15px) | 175 | 65 (110) | 73 (102) |
| 검출된 기공 (면적 13) | 189 | 72 (117) | 77 (112) |

**3x3 median이 폭 1~2px 구조를 지우고 있었다.** 대비 96·98이 통과 후 6으로 무너졌고,
살아남은 결함들은 102~112를 유지했다. 실패는 이진화가 아니라 **그 앞단의 노이즈 제거**에 있었다.
median을 끄자 14/14, 오검출 0, F1 1.000이 됐고 **처리시간도 19.1ms에서 2.58ms로 줄었다**
(median3가 C++ 실행시간의 대부분을 쓰고 있었다).

### 5.3 "median은 나쁘다"로 끝내지 않기 — 뒤집히는 지점을 찾았다

이 데이터에서 median이 손해였다고 해서 빼는 게 맞다고 일반화하면 조건을 빼먹은 주장이 된다.
노이즈 σ를 키워 가며 같은 정답 위에서 다시 쟀다(`tools/sweep_noise.py`).

| 노이즈 σ | median3 F1 | median3 오검출 | 없음 F1 | 없음 오검출 | 유리한 쪽 |
|---:|---:|---:|---:|---:|---|
| 3.5 (기본) | 0.923 | 0 | **1.000** | 0 | 없음 |
| 9.0 | 0.923 | 0 | **1.000** | 0 | 없음 |
| 16.0 | 0.923 | 0 | **1.000** | 0 | 없음 |
| 17.0 | 0.923 | 0 | **1.000** | 0 | 없음 |
| 18.0 | 0.923 | 0 | **0.966** | 1 | 없음 |
| 19.0 | **0.923** | 0 | 0.778 | 8 | median3 |
| 22.0 | **0.923** | 0 | 0.243 | 87 | median3 |

**σ 18과 19 사이에서 뒤집힌다.** 결함 대비가 약 100인 이 영상에서, 노이즈가 그 5분의 1을
넘어서면 median을 빼는 순간 오검출이 급격히 늘어난다. 그래서 결론은
"median을 빼라"가 아니라 **"결함 대비 대비 노이즈가 작으면 median이 가는 결함만 지우고 손해다.
그 비가 무너지면 반대가 된다"** 이고, 현장에서는 이 비를 재서 정할 문제다.
median3의 F1이 σ 전 구간에서 0.923으로 고정인 것도 같은 이야기다 — 지워진 스크래치 2개는
노이즈와 무관하게 계속 안 잡힌다.

## 6. 에러·함정 기록

1. **헤더 누락** — `<array>`·`<cctype>` 없이 컴파일 실패. 추가해 해결(1차).
2. **셸이 바뀌면 실행 파일이 죽는다** — `PATH`에 mingw64/bin이 없는 셸에서 실행하면
   0xC0000005로 죽었다. MinGW 런타임 DLL(libstdc++ 등)을 못 찾은 것인데 **DLL 없음이 아니라
   접근 위반으로 표시**돼 코드 버그로 오해했다. 실제로 min_area 값을 바꿔 가며 원인을
   찾다가, 직전에 성공한 명령까지 죽는 것을 보고 환경 문제로 방향을 돌렸다.
   `-static` 으로 빌드해 닫았다. **재현 조건이 코드가 아니라 셸일 수 있다.**
3. **재현율만 보면 정반대 결론이 나온다** — Otsu는 재현율 1.000이다. 정밀도 0.030을 같이
   보지 않으면 "전역 임계가 전부 잡는다"는 잘못된 결론이 된다.
4. **정답이 없으면 개선을 셀 수 없다** — 1차의 "후보 235개"는 많다는 인상일 뿐 수치가 아니었다.
   정답 CSV를 만들고 나서야 F1 0.058 → 1.000이라고 말할 수 있게 됐다. 이때
   **RNG 호출 순서를 건드리지 않아 1차 영상과 바이트가 같음을 `cmp`로 확인**하고 진행했다.

## 7. 개발 순서

1. g++ 미설치 확인 → MinGW-w64(WinLibs, UCRT) 설치, g++ 16.1.0
2. C++ 파이프라인 작성 → 헤더 누락 해결
3. 합성 데이터 생성기 → 기준 구현 → 대조. 첫 실행에서 바로 일치
4. 결함 14개 대비 후보 235개를 확인하고 원인을 조명 불균일로 특정 (1차 종료)
5. **정답 CSV 추가** — 영상 바이트 불변을 `cmp`로 확인하고 진행
6. **Sauvola 국소 적응 임계 구현**(C++·기준 양쪽, 적분영상) → 바이트 대조 통과
7. `-static` 빌드로 셸 의존 제거 (§6-2)
8. 정답 대비 채점 도구 작성 → Otsu F1 0.058, Sauvola 0.923 확인
9. 놓친 2건을 추적해 원인이 median3임을 국소 대비 측정으로 특정 → 끄고 F1 1.000
10. 노이즈 σ를 키워 뒤집히는 지점(18~19)을 찾아 조건부 결론으로 정리

## 8. 이 문서로 말할 수 있는 것과 없는 것

- 말할 수 있는 것: 전처리·이진화·연결요소 알고리즘을 **직접 구현**했고, 독립 기준 구현과
  **바이트 단위로 일치**하며, 정답 대비 F1을 **0.058에서 1.000으로** 올린 과정과 근거.
  성능 저하의 원인을 알고리즘 단계별로 분리해 특정한 방법.
- 말할 수 없는 것: 이건 **합성 영상**이다. 실제 촬영본의 빛 반사·초점 흐림·모션 블러는
  다루지 않았다. 결함 종류도 기공·스크래치 2종뿐이다. "현장 검출 성능"으로 인용하면 안 된다.
